# Recall: evidence has a timestamp

**Goal.** Answer naturally and quickly with one tool, web search, while treating “what did I ask on 3 November, and is it still true?” as retrieval plus verification. A plausible reconstruction is not memory.

**Flow.** A dependency-free Node server accepts a message and the browser’s IANA timezone. Before writing the new turn, SQLite retrieves prior question/answer pairs: an explicit local calendar date first, otherwise FTS5 lexical matches. The last 16 messages provide conversational continuity. Bounded retrieved records include original timestamps and sources, not model-generated summaries. The model then answers directly or calls the sole `web_search` function. Independent queries run concurrently through Tavily. A maximum of six queries, three model turns and a 90-second request deadline bounds latency and cost. Real model text streams over SSE; disconnecting cancels work.

**Memory versus evidence.** Each completed answer is stored with its cited snippets, URLs and retrieval times. Historical citations become `[Hn]`; this turn’s search evidence becomes `[Sn]`. Rechecking a shortlist means recovering its actual entities, searching their current official pricing/release notes, and comparing equivalent plans, currencies and billing periods. The prompt distinguishes changed, apparently unchanged and unverified. Retrieval time is never called a publication or change date. Missing dated history produces a direct explanation instead of a fabricated conversation. Freshness requests force search and bypass the five-minute local cache. Provider-side index freshness is still not guaranteed.

**Why this shape.** SQLite transactions and FTS5 make the record durable, inspectable and simple to run. Native Node HTTP, fetch, SQLite and browser DOM remove framework setup and keep the entire path explainable. No embeddings call is needed before first-token generation. One small orchestration loop, injected providers and deterministic tests are easier to reason about than a multi-agent planner. Server-side credentials, local-only binding, same-origin guards, plain-text rendering, safe source links, query limits and explicit failure states constrain the attack surface. Retrieved text is treated as untrusted evidence, never instructions. Unknown citation IDs are marked unverified rather than turned into links.

**Considered and rejected.** A vector database would improve paraphrase recall but adds infrastructure and opaque retrieval failure modes before lexical/date recall is measured. A running LLM summary could be cheaper long-term, but risks losing the exact prior price or date the challenge tests. An agent framework and multiple specialized agents add abstraction, model hops and debugging cost without a necessary second tool. A JSON history file is simpler initially, but gives up transactional writes and indexed lookup. A fancy frontend would not improve the central architecture.

**Limits and another week.** This is a local single-user prototype, not a production account system. Temporal parsing covers common English dates, not arbitrary ranges; “last Tuesday” uses the most recent prior Tuesday and explains the assumption when relevant. FTS can miss semantic matches, bounded context can omit older detail, and source-ID validation does not prove factual entailment. Search excerpts cannot establish every historical change. Live API behavior has not been tested without credentials. Next: a labeled temporal/revalidation evaluation set with live citation/claim checks, p50/p95 latency and cost measurements, optional hybrid retrieval measured against FTS, explicit correction/version semantics, and authenticated user isolation before hosting.
