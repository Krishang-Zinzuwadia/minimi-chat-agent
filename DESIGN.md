# Design: memory first, current evidence second

**Goal.** Preserve what the user actually asked and answered, then research what changed without silently rewriting the past. The challenge requires JavaScript/TypeScript on Node, one web-search tool, an easy npm entrypoint and explainable design. Next.js provides both a polished client and a conventional Node development server; no separate backend service is necessary.

**Request flow.** A Route Handler validates a bounded JSON body and IANA timezone, checks the authenticated owner, and acquires a PostgreSQL lease for the conversation. The agent retrieves recent messages and relevant prior question/answer pairs before saving the new question. It resolves explicit dates deterministically in the user's timezone. Without a date, PostgreSQL full-text search finds topic matches across that owner's conversations. A missing dated conversation is reported rather than invented.

**Model and one tool.** OpenAI Responses runs `gpt-6-luna` with low reasoning, `store:false`, streamed text and encrypted reasoning continuation between tool rounds. Its only callable function is `web_search`, backed by Firecrawl's search-and-extract endpoint. Freshness requests force that tool and bypass cached page data. Three model rounds, six deduplicated queries, bounded excerpts and deadlines control latency and spend. Independent queries in a batch run concurrently. Failed research is explicitly reflected in the final response.

**Provenance.** PostgreSQL stores timestamps, text and JSONB source snapshots. Retrieved historical sources receive `H` labels; newly searched sources receive `S` labels. Even the same URL remains separate across time. Unknown citation identifiers are marked unverified. Only cited sources are persisted with the final answer. Search text and past content are untrusted evidence, never instructions. Streaming is provisional; the final event replaces it with the saved, validated response.

**Security and deployment.** Local mode accepts loopback requests only. Hosted mode verifies Cloudflare Access JWT signature, issuer, audience and expiry with jose; every query is owner-scoped. Same-origin checks, parameterized SQL, safe links and disabled remote Markdown images reduce exposure. Abort signals stop provider work. Atomic database admission permits one active turn per owner and 60 admitted turns per UTC day; token-scoped leases prevent overlap. Neon HTTP avoids persistent connection pools in Workers. vinext builds the same Next application for Cloudflare, while public routes remain disabled until Access, secrets and live smoke tests are ready.

**Alternatives.** Hono would add a separate routing layer without helping this small app. SQLite was simpler locally but unsuitable for persistent multi-instance Workers storage. Embeddings/vector search would improve semantic recall but add cost, indexing and another service dependency; Postgres full-text search is inspectable and sufficient for the challenge. A generic agent framework would obscure the small bounded loop. Separate search and scrape tools would violate the chosen single-tool boundary.

**Trade-offs and next week.** Lexical recall misses paraphrases; date rules cannot express every natural-language range; capped context can omit history. A citation is not proof of factual correctness. Demo memory is temporary, not Neon. Provider mocks and embedded PostgreSQL are not live integration evidence. Next week: verify real Workers/Neon/provider behavior, add currency-aware budgets and request-rate limits, record structured per-step timings and token usage, improve semantic reranking and date clarification, test multi-user isolation end to end, and add resumable streams with idempotent turn IDs. Do not call the deployment production-ready before these checks and the setup runbook are complete.
